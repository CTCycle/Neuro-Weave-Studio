## Export recovery evidence (NW-T5-01 subset)

Focused `RuntimeController` failure-injection tests now cover:

- conversion worker failure: the error is typed as `export_conversion_failed`, the previous published bytes remain unchanged, staging files and job workspace are removed, and no active job remains;
- atomic publication `os.replace` failure: the error is typed as `artifact_publish_failed`, the previous published bytes remain unchanged, temporary publication and workspace are removed, and no active job remains;
- cancellation during conversion: the job reaches the cancelled/terminated state, the pre-existing artifact is preserved, worker workspace and temp publication are removed, and no active job remains.

These tests inject controlled worker/publication failures; they establish cleanup and preservation behavior, not a naturally occurring runtime crash. Valid matrix artifacts and neighboring unsupported/invalid API cases passed in the same run. No reproducible in-scope implementation defect was found, so no production behavior was changed.

An additional experimental standalone Pytest-worker probe of ONNX `external_data=always` encountered Windows `Access is denied` while canonicalizing its deep temporary path; the exact diagnostic and disposition are recorded in [`logs/onnx-external-data-pytest-probe.txt`](logs/onnx-external-data-pytest-probe.txt). The same external-data path then succeeded from a standalone worker and, more importantly, through the official launched application's in-app export with browser download event, exact archive/member hashes, checker and CPU inference evidence. The discrepancy is confined to that experimental test-harness invocation; it did not reproduce as a product failure and is not used as the acceptance proof.
