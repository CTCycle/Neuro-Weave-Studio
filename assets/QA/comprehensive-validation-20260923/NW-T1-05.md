## Scope

This slice verifies that Settings remains an informational page with separate
Node Library and Runtime Environment management surfaces. It also verifies
that Training requires a saved model and registered dataset, creates only a
session draft, disables **Start training**, and loses the draft after a full
reload. It does not claim training execution, job persistence, or model weight
updates.

No application or public API code changed. The new serial browser spec covers
the boundary and uses a run-scoped saved project plus a dataset registered
through the dataset UI. The tested application source stayed at the base

## Results

The serial Playwright command passed **1 test in 42.8 seconds**. The E2E
workflow verified:

- Settings exposes no buttons, form fields, selects, text areas, editable
  content, switches, checkboxes, or forms. Its Node Library and Runtime
  Environment links navigate to `/nodes` and `/environment` separately.
- The fresh database has no saved projects or registered datasets. Training
  shows both prerequisite messages and disables both draft-creation entry
  points.
- After a saved model and UI-registered dataset are available, the UI creates
  a draft with the requested name, model, dataset, 7 epochs, and batch size 16.
  The card says `DRAFT · not started`; **Start training** remains disabled.
- The draft survives SPA navigation from Training to Settings and back. A full
  reload removes it, while the creation entry point remains available.
- No training or jobs API mutation was sent, no training key appeared in
  browser storage, and browser page, console, request, and HTTP diagnostics
  were empty.

The Codex in-app Browser independently showed the Settings boundary, the
missing-model/dataset prerequisite state, and the draft with its model,
dataset, epoch and batch values. The draft remained during in-app navigation
and disappeared after reload. See the [in-app Browser observation](evidence/nw-t1-05-inapp-browser-observation.md)
and the [draft screenshot](evidence/nw-t1-05-training-session-draft.png).

The in-app inspection's disposable model was seeded through the local project
API because Model Builder reported that no operational execution backend was
available for creating a new model in this launch. The dataset was registered
through the UI. These records were only prerequisites for observing the
session-only Training workflow; no training request was made.
