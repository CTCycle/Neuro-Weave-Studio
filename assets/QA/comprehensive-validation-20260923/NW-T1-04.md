## Scope

This slice covers restoring the last selected runtime backend and its saved
API, device, and memory policy; safe reconciliation when a device, backend, or
nested preference is stale; and usable in-memory selection when browser storage
is unavailable. Runtime preference evidence does not certify runtime execution,
training, or export.

The per-backend preference map remains in
`neuroweave.runtime-preferences.v1`. The active backend is stored separately
in the versioned key `neuroweave.runtime-preference-backend.v1`. Stored
configurations are shape-checked before use, and invalid memory-policy shapes
are rejected without throwing.

The browser fixture exposes selectable PyTorch and TensorFlow backends, Keras
and Native APIs, CPU/GPU devices, and multiple memory policies. It verifies:

- Existing PyTorch device and memory-policy reload behavior.
- Restoration of the last active TensorFlow backend, Native API, GPU device,
  and 2048 MB memory limit after reload.
- Reconciliation of a retired GPU device to a valid CPU/default preference.
- Fallback from an unavailable active TensorFlow backend to the preferred
  available PyTorch backend, including updated storage.
- Recovery from a malformed nested memory policy to a valid default.
- Continued runtime selection in memory when local-storage reads and writes
  throw; cross-reload persistence is not claimed for that case.

The controlled metadata fixture is used only to validate preference
selection and persistence. The workflow did not submit a job or claim runtime
execution. See the [browser diagnostics](evidence/nw-t1-04-browser-diagnostics.md)
and the rendered [post-reload Environment screenshot](evidence/nw-t1-04-active-preference-reload.png).
