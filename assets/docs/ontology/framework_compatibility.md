# Framework Compatibility

Last updated: 2026-09-12

A node definition contains declarative implementation mappings keyed by `keras`, `tensorflow`, `pytorch`, and `jax`. The model execution profile resolves to `keras` when `keras_enabled=true`, or to the persisted backend when it is false. The checked-in manifest is the source of implementation and parameter capability truth; the loader normalizes one unified catalog and does not promote unsupported nodes into a portable set. The current catalog contains 149 manifests, with 143 Keras mappings and 108 verified native mappings for each TensorFlow, PyTorch, and JAX/Flax target. Native support covers the verified common layer, mathematical, merge, input, and output-adapter subset; advanced layer variants and transformer nodes remain explicitly unavailable. The native compiler controls are separate live capabilities, not assumptions about manifest support. Unsupported node/parameter combinations produce typed compatibility diagnostics and block compilation; there is no identity fallback.

Runtime/API and native-compiler availability is isolated discovery data returned by `/api/metadata`. Missing optional dependencies or an unavailable compiler disable only the affected capability with an explicit reason; matching discovery snapshots may be reused until the environment fingerprint changes. Source generation remains available where the manifest/exporter contract is valid. The validation and node catalog surfaces keep Keras portability, native backend support, compiler availability, and runtime execution as separate concerns.
