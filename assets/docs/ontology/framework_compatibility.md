# Framework Compatibility

Last updated: 2026-08-21

A node definition contains declarative implementation mappings keyed by `keras`, `tensorflow`, `pytorch`, and `jax`. The model execution profile resolves to `keras` when `keras_enabled=true`, or to the persisted backend when it is false. The checked-in manifest is the source of implementation and parameter capability truth; the loader must not promote nodes into a portable set. Native TensorFlow and JAX/Flax capabilities are currently disabled pending runtime parity tests. The native PyTorch core currently includes dense, dropout, flatten, embedding, LSTM/GRU, Conv2D, MaxPool2D, rank-aware BatchNorm/LayerNorm, and common add/residual/skip/concatenate merges. Unsupported node/parameter combinations produce typed compatibility diagnostics and block compilation; there is no identity fallback.

The current local parity evidence found Keras and PyTorch available to the isolated worker probe, while TensorFlow, JAX, and Flax may be missing or unavailable on native Windows. Native TensorFlow and JAX therefore remain disabled for manifest nodes until dependency-backed runtime and exporter parity is proven; no capability is promoted from source inspection alone. The complete inventory and commands are recorded in `assets/QA/native-target-audit-2026-08-18.md`. The validation and node catalog surfaces expose the distinction between Keras-enabled portability, native PyTorch source support, and unavailable native runtime inference.
