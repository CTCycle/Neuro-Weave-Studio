# Serialization and Versioning

Last updated: 2026-09-03

The canonical graph is version 5 and the portable NeuroWeave project bundle is version 6. A graph stores one `model_configuration` value with explicit `keras` and `native` branches; native TensorFlow, PyTorch, and JAX compiler settings are independent and disabled by default. Nodes persist their canvas lock state, and `output_bindings` stores explicit node-port selections; an empty selection means that unconsumed value-producing terminal ports are inferred as outputs. Output adapter nodes remain supported as optional semantic/task boundaries, but they are not required to terminate a workflow.

Input node shapes are persisted and exported as feature-only dimensions. For example, `[8]` is the canonical tabular shape and `[32, 32, 3]` is the canonical image shape. The runtime validation and execution boundary injects an unknown batch dimension, so the corresponding runtime shapes are `[None, 8]` and `[None, 32, 32, 3]`. `model_dump`, database writes, imports, revision snapshots, undo/redo, and export serialization all pass through this boundary and must never persist the runtime batch dimension.

Readers accept only the current graph schema 5 and project bundle format 6. Persisted databases are upgraded only through the forward Alembic chain, including the current head `20260915_remove_graph_schema_tracking` after `20260910_dataset_registrations`; the earlier canonical graph migrations include `20260827_canonical_model_configuration`, `20260901_model_builder_graph_boundaries`, and `20260902_runtime_batch_shapes`. There are no runtime dual readers, aliases, schema-adoption paths, or compatibility shims.

Custom node templates have a separate monotonically increasing authoring revision stored in `custom_node_definitions.version`. That value identifies edits to the reusable template only. It is not a canonical graph node `definition_version`. Mathematical and sequential templates materialize into built-in manifests before graph persistence, so saved model nodes continue to contain only built-in manifest IDs and versions. Editing or deleting a custom template therefore cannot silently change an already saved model. Verified Hugging Face references are not serialized into project graphs because they remain non-executable reference metadata until a trusted adapter exists.

Empty quantization objects are treated as disabled when they contain no meaningful nested value. Meaningful `false`, `0`, strings, and nonempty nested values remain configuration. Output counts and input counts are derived from the active node catalog and graph topology rather than stored as a second source of truth.

Keras architecture imports treat `input_shape` as feature-only. `batch_shape` and `batch_input_shape` lose their leading `None` or fixed batch value; a discarded fixed batch size produces an import warning because batch is runtime-only. The normalized feature rank selects tensor, sequence, or image input manifests, and malformed or empty shapes are rejected.

Graph schema 5 stores model input shapes as feature dimensions only. Runtime batch is not part of persisted architecture state. For example, a tabular model with 20 features stores `[20]`; validation, source generation, and workers consume the equivalent runtime shape `[None, 20]`. `input.parameter` remains an explicitly unbatched parameter shape and is not transformed by the batch-shape migration. Empty quantization placeholders are omitted rather than serialized as active configuration.

A project bundle stores `execution_backend`, `keras_enabled`, the graph, and revision-independent export settings. Built-in node definitions have stable IDs and integer versions. Canonical writes always emit graph version 5 and bundle version 6. The immediately preceding graph version 4 and project bundle version 5 are accepted only at the import/model-validation boundary and are normalized once to the canonical representation. Unsupported older or future versions are rejected. Project revisions are application history, not schema versions, and custom-template revisions are authoring history, not graph-schema or manifest versions.

Generated source snapshots retain the model execution profile used for the current revision. A `.keras` binary is an initialized artifact, not a portable project bundle. A `.keras` architecture import reads only allowlisted configuration metadata and creates a new canonical graph. Keras `batch_shape` and `batch_input_shape` values have their leading batch element removed during import, while `input_shape` is already interpreted as feature-only. Weights, optimizer state, custom Python objects, remote repository code, and custom-template identities are not serialized into the NeuroWeave project.
