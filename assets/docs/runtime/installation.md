# Installation

Last updated: 2026-10-21

Run `start_on_windows.ps1` from the repository root and select **Install or repair base dependencies** when local runtimes or dependencies are missing. Installation synchronizes the locked Alembic/file-lock runtime dependencies and initializes or validates the configured SQLite database against the current schema baseline before rebuilding the frontend. Databases stamped with removed migration revisions or populated databases without an Alembic revision must be recreated explicitly; the launcher does not delete them. A successful frontend `npm ci` records `runtimes/cache/frontend-dependency-state.json` using the SHA-256 fingerprint of `package.json`, `package-lock.json`, and the pinned Node.js version; the state is published only after `npm ci` succeeds. A successful production build records `runtimes/cache/frontend-build-state.json` using the sorted content fingerprint of the production Angular inputs and the pinned Node.js version; its timestamp is diagnostic only. These generated state files are ignored with the rest of `runtimes/` and are recreated automatically when absent. After the frontend dependencies are installed, select **Rebuild frontend** whenever a standalone production frontend build is needed; this does not synchronize backend packages. The launcher asks for a **Development** profile (including Ruff, Pyright, and pytest) or a **Standard** profile (runtime dependencies only). It uses pinned repository-local Python 3.13.14, uv 0.12.0, and Node.js 22.23.1 under `runtimes/`; subsequent launches validate the exact interpreter and installed environment. All runtime/download, application, frontend, tooling, pytest, and temporary test caches are written beneath the single canonical root `runtimes/cache`; persistent application data remains under `data/runtime`. Set `NEURO_WEAVE_RESOURCES_DIR` or use `-ResourcesDir` when the default data directory is not desired.

Keras 3 is a required core dependency and is not an execution-backend choice. Use **Manage compute backends** or `start_on_windows.ps1 -Action ManageBackends` to choose from the numbered configurations: none, PyTorch GPU/CUDA, PyTorch CPU-only, TensorFlow CPU-only, JAX CPU-only, all supported native-Windows backends, or all backends CPU-only. PyTorch `Auto` selects the pinned CUDA 12.6 wheel only when the detected NVIDIA driver supports it, otherwise it uses the CPU wheel. Use `-Acceleration CPU` to force CPU, including with `-Backends pytorch` or `-Backends all`. TensorFlow and JAX are CPU-only on native Windows; JAX CPU support is experimental, and GPU execution requires a separate WSL2/Linux environment. The JAX extra installs bounded `jax` and `flax` packages. Backend management uses the locked uv extras, records installation output, probes actual worker capability, and attempts to restore the previous extra set after a failed update. Base dependency repair preserves both the recorded and currently detected optional execution backends; only an explicit backend-management selection removes one. Core-only mode supports source generation but exposes no operational inference backend until a probe succeeds.

The canonical environment file is `settings/.env`. The shared environment loader creates it from `settings/.env.example` when it is absent, for both launcher and direct backend startup, without overwriting an existing file. `start_on_windows.ps1 -Action Install -InstallationType Standard` installs the base environment; `start_on_windows.ps1 -Action ManageBackends -Backends tensorflow` adds one optional backend. Never commit `settings/.env` or other `.env` files.

For native PyTorch `torch.compile` on Windows, install the Visual Studio C++ workload and Windows SDK, then launch the application from an x64 Native Tools Command Prompt so the compiler environment is inherited. The runtime dependencies include the native JAX ONNX exporter (`jax2onnx`) when JAX is installed; no TensorFlow bridge is required for native JAX ONNX export.
