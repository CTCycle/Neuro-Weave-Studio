# Frontend Architecture

Last updated: 2026-09-17

The canonical Angular application lives in `app/client/src/app`. The standalone `AppShellComponent` owns primary navigation, route-level components are lazy-loaded from `app.routes.ts`, and typed API access is isolated under `core/api` against the relative `/api` path. `ApiService` remains the general application client while `CustomNodeApiService` owns the installation-wide custom-template CRUD surface. Framework-neutral graph contracts live in `domain/types.ts`; custom authoring-template contracts live in `domain/custom-node.types.ts`; editor-only records live in `domain/editor.types.ts`.

The model catalog and model workspaces are reached through `/models`, `/models/:modelId`, `/models/:modelId/compilation`, `/models/:modelId/validation`, and `/models/:modelId/export`. New and existing architecture authoring is isolated under `/builder` and `/builder/:modelId`. Dataset and training bootstrap workspaces are available at `/datasets` and `/training`. The `/nodes` route provides a searchable node library with an index/detail layout for the complete built-in manifest catalog plus installation-wide custom templates. Built-ins are inspection-only; custom definitions expose edit and delete actions. The `/settings` route is a conventional application-settings shell with a left navigation rail and flat content sections. Its General section is intentionally minimal because no typed runtime-editable global settings exist yet; related Node Library and Runtime Environment links remain separate management destinations. Environment-backed launch configuration is not exposed or duplicated in the Settings UI. All of these routes are lazy-loaded primary destinations.

`AppResourcesService` exposes independent signal-backed catalog, project, runtime, and capability readiness; each route explicitly loads only the resources it consumes, deduplicates concurrent reads, and provides resource-level retry. The Nodes workspace consumes the same shared manifest resource instead of issuing a second built-in catalog request. Custom-template loading remains independent so a custom-template API failure does not prevent the immutable built-in catalog from being inspected. The root resource service performs no network work in its constructor.

`TensorInspectionCoordinator` is the root-provided session state for validated-model inspection. `TensorInspectorModalComponent` is mounted once by `AppShellComponent`; both the Builder canvas and the read-only model preview pass only `{ projectId, revision, nodeId }`. The coordinator owns job polling/cancellation, session cleanup, node and port selection, bounded view loading, axis choices, compatible-view preservation, and recoverable expiry/errors. No graph editor store or persisted project is mutated by an inspection.

`GraphEditorStore` owns the editable graph, history, selection, and serialization; `BuilderTabsStore` retains a separate graph session and saved baseline per open model tab. This prevents browsing or switching models from mutating another editable draft. Foblex renders the graph through an adapter; it is never the persisted source of truth. Reusable standalone components implement catalog browsing, properties, validation, code preview, functional validation, filesystem browsing, and model commands. Node rendering is registry-based through app-owned editor records and manifest implementation mappings.

The Nodes route keeps the canonical built-in catalog and custom authoring templates visually distinct. Built-in detail views expose version, semantic role, ports, parameters, shape-rule identity, operation family, task hint, deprecation state, all declared implementation mappings including unsupported mappings and their notes, documentation references, and lock status. The custom-node wizard first selects one of three authoring kinds: mathematical operation, sequential block, or public repository reference.

Mathematical templates reuse the shared KaTeX surface for direct LaTeX or guided equation entry. The server validates and normalizes the formula to NeuroWeave's existing safe single-input expression language. `CustomNodeMaterializerService` turns the template into the canonical built-in `math.expression` graph node before the graph is persisted. Sequential templates use the same manifest-driven parameter parsing and controls as ordinary Builder authoring; when inserted, the materializer creates the referenced built-in nodes, applies the validated parameter maps, and connects compatible active ports in order. Hugging Face definitions are public-repository references only: the server verifies and pins them, while the Builder renders them disabled until a trusted execution adapter exists. No custom template ID is written into the canonical model graph.

`ExperimentDraftsService` owns only the session-only training and custom metric/loss drafts; persisted dataset registrations are independent. `AppResourcesService` owns the dataset summary resource and `DatasetWorkspaceState` owns one selected registration. The Datasets route uses `FilesystemBrowserComponent` and `GET /api/filesystem/browse` to navigate the local machine and select real file or directory paths. `DatasetWizardComponent` uses the typed capability registry, path-derived formats, lightweight inspection, default role assignments, authoritative validation, and create-only registration without copying dataset bytes. The durable dataset workspace owns Overview, Validation, I/O, Processing, and Split: I/O persists bindings and structural fields, Processing persists real source interpretation and re-inspects, and Split persists population and declarative fractions/strategy without materialization. The Training route pairs a saved model with a persisted dataset summary but remains a non-executing session draft; no worker, fit loop, weight update, checkpoint, or training database contract is implied. The Metrics route treats the server-owned compilation catalog as read-only while allowing custom metric/loss authoring through direct LaTeX or a guided equation builder rendered with KaTeX.

`/api/metadata` supplies runtime `execution_backends`, per-backend API/compiler status, discovery state/source/time, and one capability-driven `configuration.compilation_capabilities` tree. `POST /api/execution/discovery` checks only the selected backend/API pair; compute routes observe it at 500 ms intervals with a bounded deadline and stop observing when navigated away. Unchecked metadata remains useful for the shell but cannot start a job until that pair is verified. Runtime discovery skips absent packages, records isolated worker results in a schema-versioned fingerprinted `runtimes/cache/environment-discovery.json` snapshot, and validates a matching snapshot on demand; explicit Environment controls remain the refresh path. A model's `execution_backend` and `keras_enabled` are persisted together; the Builder exposes them as a compact native-backend selector and explicit optional Keras API-layer toggle. Backend availability informs capability controls and runtime preferences, but it does not replace the persisted model profile.

The workspace preserves the drafting-board palette while reflowing at 1440/1200/1024px breakpoints. The Builder is dedicated to graph authoring, metadata, validation, and saving; compilation configuration and source generation belong to the Compilation page, while artifact downloads belong to the Export page. Its fixed-height editor uses a tab bar, compact authoring toolbar, node catalog, Foblex canvas adapter, inspector, and a bottom validation region with a pointer-resizable splitter. The description is edited through a small metadata popover and remains part of the canonical Builder tab/project metadata. The canvas has local minimap visibility and a focus mode that keeps the same Angular/Foblex editor instance mounted while temporarily hiding nonessential chrome. At 1024px and below the Catalog and Inspector become explicit drawers; the canvas and validation region remain within the viewport without document scrolling. Catalog, workspace, workflow, dataset, training, environment, metrics, nodes, and settings surfaces share the available content width and a stable scrollbar gutter.
