# Persistence

Last updated: 2026-09-10

NeuroWeave currently uses one SQLAlchemy schema backed by SQLite. Alembic is the authoritative schema lifecycle and `repositories.base.Base.metadata` is its autogeneration source of truth. A project is the model/workflow aggregate exposed by `/api/projects`; installation-wide reusable authoring definitions are persisted separately from project graphs.

The selected backend and SQLite connection parameters live only in `database-config.json` under the application resource directory. The file is validated against a versioned schema and replaced atomically. It is independent of the database so startup and database repair do not depend on a working connection. On first startup, legacy `DATABASE_SQLITE_PATH`, `DATABASE_CONNECT_TIMEOUT`, and `NEURO_WEAVE_*` settings are imported once; migrated keys are then removed from `.env` and the process environment. `.env.example` contains launch configuration only.

All application preferences, including CORS origins, log level and file, runtime paths, and timeout values, live in the singleton `application_settings` row of the selected database. Each database has its own settings row. Switching databases waits for API requests to drain, refuses while runtime jobs are active, validates the target schema, activates its repository context, and loads its local settings. Switching never copies projects, datasets, or settings. The existing migration history is preserved and extended to add the settings table.

The canonical project tables are `projects`, `project_graph_settings`, `project_nodes`, `project_edges`, `project_revisions`, and `generated_code_snapshots`, plus Alembic's `alembic_version` table. Projects own current graph settings, ordered nodes, and ordered edges. Composite project/node foreign keys prevent an edge from connecting nodes belonging to another project. Project revisions are immutable graph snapshots. Generated source is linked to a specific project revision and is returned only for the current revision.

Installation-wide authoring definitions use focused tables outside the project aggregate. `custom_metric_definitions` stores persisted user metric/loss equations. `custom_node_definitions` stores user-authored node templates with stable relational identity, a monotonically increasing template revision, kind, normalized display name, category, timestamps, and a bounded JSON definition payload. Built-in node manifests are checked-in application resources and are never copied into this table. Custom templates therefore cannot overwrite, edit, or delete built-in manifests.

Dataset registrations use one `datasets` table. Relational columns store identity, type, format, available/selected sample counts, validation status, and creation/update timestamps. `definition_json` contains the normalized typed source/binding/relationship/sequence/subset/split definition; `inspection_json` contains the compact registration-time schema/count/shape snapshot; and `validation_json` contains timestamped bounded findings and warnings. No sample rows, image bytes, arrays, previews, partition files, or source copies are persisted. The repository participates in the existing unit-of-work and services own commit boundaries. List/get compute current source availability from the stored paths without mutating the snapshot. Persisted revalidation updates the validation state and replaces inspection/counts only after a successful inspection. Deleting a registration deletes only the row.

`custom_node_definitions.spec_json` is authoring metadata, not an alternate executable graph representation. Mathematical templates store the original LaTeX-style formula plus the server-normalized safe expression used when the template materializes as built-in `math.expression`. Sequential templates store an ordered list of built-in manifest identities and fully normalized parameter maps validated against those manifests. Public repository definitions store Hugging Face coordinates, the requested revision, the exact resolved public commit, available library/pipeline metadata, and an optional class/entrypoint hint.

When a mathematical or sequential template is inserted in the Model Builder, it is materialized into ordinary canonical graph nodes before persistence. Saved project graphs therefore continue to contain only built-in `definition_id` and `definition_version` references. They never contain a custom-template ID or template revision. Editing or deleting a template cannot retroactively alter a model that was already created from it.

Repository references are not materialized into graph nodes. The persistence layer does not store executable Python or JavaScript, trusted remote-code flags, downloaded repository code, arbitrary callables, authentication tokens, or unverified mutable repository state. Hugging Face references are verified while saving and pinned to a resolved commit, but they remain reference metadata until a trusted runtime adapter exists.

The model catalog uses the existing `/api/projects` contract and enriches each `ProjectSummary` with batched node/edge counts and `has_generated_source`. The service obtains graph summaries and current-revision source-snapshot state through repository queries inside the existing unit of work, so catalog cards do not issue per-model detail requests. A source snapshot is associated with the model's current revision and persisted execution profile; saving a new revision therefore invalidates the previous compiled state without a schema change.

Known queryable values use relational columns. JSON is limited to node parameters, dynamic graph configuration maps, immutable revision snapshots, expression trees, and bounded custom-definition payloads. Enums are strings with checks, UUIDs or stable identifiers are application-generated strings, and timestamps use a UTC-normalizing SQLite type.

Repositories never commit independently. A unit of work supplies one SQLAlchemy session to focused project, graph, revision, code-snapshot, metric, and custom-node repositories. Services own transaction boundaries; API routes only validate requests, call services, and map domain errors to HTTP responses. Optimistic revision checks prevent stale project updates from overwriting newer saves.

`repositories/initializer.py` coordinates the Alembic environment. Missing or empty SQLite files are upgraded from base to head. Every application startup checks the current Alembic heads and applies pending revisions before repository sessions are created. A database-local lock serializes concurrent migration attempts, and one SQLAlchemy transaction covers migration execution. ORM registration includes both the canonical project models and installation-wide custom-node models before the migrated table set is compared with `Base.metadata`.

Databases that contain tables but do not carry the current Alembic history are unsupported. They are rejected without stamping, adoption, translation, or mutation; there is no legacy schema reader or compatibility path. The application exposes no destructive reset path.
