# Backend Architecture

Last updated: 2026-09-28

`app/server/app.py` is the FastAPI application factory. Routers translate HTTP contracts, services own validation, import, export, repository transactions, filesystem navigation, and runtime orchestration, and the domain models define the graph, execution profile, runtime, job, and filesystem contracts. Lifespan creates the catalog, repository context, and one application-scoped `services.runtime_controller.RuntimeController`; the controller is shut down and joined before repositories are disposed. Database verification, catalog loading, and controller construction are essential startup work. Optional framework and hardware discovery is on demand through `POST /api/execution/discovery` and never runs in lifespan.

`ModelExecutionProfile` is the backend authority for a project: `execution_backend` selects TensorFlow, PyTorch, or JAX and `keras_enabled` selects the Keras implementation versus the native implementation. The compiler and validator receive this pair explicitly, derive the manifest implementation key, and never recover a different backend from a worker preference or request-local fallback.

## Local filesystem browser

`GET /api/filesystem/browse` is a read-only local filesystem boundary for path-backed workflows. `FilesystemService` lists available roots, directories, and optionally files, returns real local paths, supports extension filtering, orders directories before files, and caps one response at 500 entries. It performs no uploads, copies, writes, database persistence, or dataset interpretation. Missing, invalid, inaccessible, and permission-restricted paths return explicit HTTP errors. This endpoint is intended for the local-first application runtime so browser-based pages can select the same filesystem paths that backend operations will later consume.

## Process-isolated runtime

The server process never imports Keras, TensorFlow, JAX, or PyTorch. `RuntimeController` discovers capabilities with short-lived probe workers and starts a new `models.ml_worker` interpreter for every functional-validation or Keras-export job. The dispatcher applies common process environment configuration, loads only the selected backend worker, and delegates lifecycle work to `models.worker_core`. `models.worker_backend.BackendWorker` defines the shared device inventory, startup configuration, metrics, synchronization, execution, and cleanup contract; `tensorflow_worker.py`, `pytorch_worker.py`, and `jax_worker.py` contain the explicit framework imports and backend-specific operations. `keras_worker.py` is limited to Keras model construction and receives checkpoint callbacks explicitly. The worker sets `KERAS_BACKEND` and allocator/device environment variables before importing Keras-dependent modules. This boundary avoids inherited accelerator state and unsafe framework reuse.

`WorkerConfiguration` is frozen and contains `api` (`keras` or `native`), the profile backend, normalized physical `device_id`, session-scoped memory policy, and session-scoped precision. Keras is operational when its selected backend probe succeeds. Native workers execute the selected TensorFlow, PyTorch, or JAX implementation directly; compiler settings are validated against the worker probe and unavailable compilers return explicit diagnostics. No native runtime path falls back to Keras.

The controller owns one lease per normalized physical device (`cpu`, `cuda:0`, `rocm:0`, `mps:0`, or `xpu:0`). Jobs on different leases may run concurrently. States are `starting`, `running`, `stop_requested`, `stopping`, `succeeded`, `terminated`, and `failed`. A lease is released only after the worker PID has been waited on and any termination escalation has completed.

Each job has a bounded workspace under `data/runtime/ml-jobs` containing immutable input/configuration, atomic status/result publication, a cancellation marker, and bounded diagnostics. Graph input is removed after worker startup; terminal workspaces are removed. At most 100 terminal records remain in controller memory. Cancellation checks surround import, initialization, construction/loading, forward execution, save/reload, and publication. Cooperative cancellation receives five seconds, then the worker process tree is terminated and, after another five seconds, force-terminated.

Keras export writes a temporary `.keras` file in the job workspace. Reload/forward-pass verification and a final project-revision check must pass before atomic replacement of the canonical export under `data/runtime/exports`; failures and revision conflicts never overwrite a prior artifact.

## Ephemeral tensor inspection

Validated, clean project revisions may submit a `tensor_inspection` runtime job through the same process-isolated controller used by functional validation. The job keeps the persisted `execution_backend`/`keras_enabled` pair exact, seeds the selected runtime, builds normally initialized (untrained) weights, performs one forward pass, and captures canonical node/port outputs. Keras uses one probe model over its symbolic tensors; native exporters return an optional trace from the same generated model. Unsupported tracing, dtype, dynamic dimension, runtime, or node combinations fail closed.

The worker publishes an atomic, filesystem-backed session under the ephemeral tensor-inspection root. Session metadata contains the stable topological index, graph depth, predecessors, successors, seed, runtime, weight source, and bounded tensor descriptors. Arrays are never written to the database: each tensor is full, sampled, or summary-only, with exact or sampled statistics and a 64-bin histogram. Per-tensor/session byte limits, ten-minute idle expiry, three-session retention, lazy bounded views, explicit deletion, startup cleanup, and controller shutdown cleanup protect backend and frontend memory.

The public contract is `GET/POST/DELETE /api/tensor-inspections/...`; the view endpoint accepts fixed axes, display axes, offsets, and a point limit. A revision check runs immediately before publication so a changed project cannot expose stale activations.

## Runtime diagnostics and limits

Metadata is runtime capability information: API capability, installed/operational backend, discovery state/source/time, discovered devices, supported memory policies, and normalized lease keys. Startup reads package inventory and a schema-versioned snapshot without importing optional frameworks. A requested backend/API pair is checked in an isolated worker, with duplicate requests joined and no more than two probes in flight; package, hardware, runtime-environment, or backend-installation changes invalidate the fingerprinted snapshot. `unchecked` means no live validation has occurred and is never rendered as “not installed.” Workers report PID, immutable configuration, lifecycle phase, exit code, cancellation/escalation state, restart reason, process RSS, and nullable framework/device metrics. Cleanup (`clear_session`, JAX cache clearing, PyTorch synchronization/cache cleanup, and garbage collection) is best effort and does not replace process teardown. PyTorch allocated versus reserved/cached memory and framework/device metrics are intentionally shown separately.

Dataset registration is a separate metadata boundary. `DatasetInspectionService` performs bounded table, image, text, and NPY/NPZ inspection; `DatasetService` validates typed source layouts, roles, subsets, declarative split definitions, and exact file-to-table relationships; and `DatasetRepository` persists only the definition, inspection snapshot, validation findings, counts, status, and timestamps. The `/api/datasets` routes are synchronous so filesystem work runs outside FastAPI's async event loop. `POST /api/datasets/{id}/validate` re-inspects a stored definition and persists valid or invalid findings; when inspection fails it retains the prior successful inspection snapshot and counts. Availability is computed from stored paths on list/get without rescanning or mutating the registration. Deletion removes only the row and never changes a user's source. Dataset loading, preprocessing transformations, split materialization, training execution, weight updates, and checkpoints remain outside this runtime boundary. Installing or removing optional packages still requires an application restart. Normal backend/device/policy changes only affect the next fresh worker; an operating-system restart is exceptional recovery for driver/runtime faults.
