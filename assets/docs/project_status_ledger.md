## Maintenance rules

Future coding agents must:

1. Inspect this ledger before substantial implementation or validation work.
2. Use it to find known defects and previously validated behavior.
3. Update affected entries after implementation.
4. Update evidence after meaningful tests, browser checks, or manual validation.
5. Never mark a component `VALIDATED` without supporting evidence.
6. Downgrade a status when a regression is discovered.
7. Close or move an issue to the resolved section only after remediation and revalidation.
8. Avoid duplicate issue entries for the same underlying defect.
9. Link detailed reports rather than copying their narratives into this ledger.
10. Keep the ledger synchronized with the repository, current runtime constraints, and the evidence actually available.

`Last Validated` records the date of the latest meaningful evidence, not necessarily the date of the source change or this document update. A historical report does not prove that a later runtime, dependency, or source revision still behaves identically; use the scope and next action to decide whether to revalidate.

## Status taxonomy

Use only these component statuses:

| Status | Meaning |
| --- | --- |
| `VALIDATED` | Implemented and confirmed by meaningful evidence at the stated scope and date. |
| `WORKING` | Believed to work from implementation and limited or indirect evidence, but not fully validated. |
| `PARTIAL` | Implemented but incomplete, degraded, or valid for only part of the expected behavior. |
| `BROKEN` | Known not to work correctly under the stated conditions. |
| `BLOCKED` | Cannot currently be validated or completed because of an external dependency, missing capability, unavailable service, hardware/toolchain constraint, or similar blocker. |
| `UNVALIDATED` | Implementation exists, but available evidence is insufficient to claim that it works. |
| `NOT_IMPLEMENTED` | The expected capability is absent from the current product. |
| `DEPRECATED` | Intentionally retained only for compatibility or scheduled removal. |

`VALIDATED` is evidence-scoped. Unit tests or source inspection alone do not establish a browser or runtime workflow as validated. Severity in the issue catalog is independent of functional status: a `PARTIAL` component may have a `LOW` issue, and a `VALIDATED` component may still have validation debt outside its stated scope.

No component is classified `BROKEN` in this bootstrap snapshot. Known unavailable paths are recorded as `PARTIAL` or `BLOCKED` with their boundary and blocker; they must not be mistaken for successful functionality.
