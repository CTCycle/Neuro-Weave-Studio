# User Flows

Last updated: 2026-09-16

The application opens on the model catalog (`/models`). Users browse or filter saved models, select one for a read-only overview, and choose a dedicated Compilation, Export, or Functional Validation workspace. The Model Builder (`/builder`) is reserved for creating a model; `/builder/:modelId` edits an existing architecture. In Builder, users set the execution backend and Keras/native mode, add nodes from the catalog, connect typed ports, configure exposed node properties, validate, and explicitly save. Multiple open models use isolated tabs. Save persists the canonical graph/profile revision; Compilation then owns capability-driven configuration, validation, and source generation. Unsaved Builder changes warn before internal navigation or browser unload.

The primary navigation also exposes Nodes (`/nodes`), Datasets (`/datasets`), Training (`/training`), Metrics (`/metrics`), Environment (`/environment`), and Settings (`/settings`). The Nodes workspace shows the complete immutable built-in manifest catalog in a searchable index/detail layout. Built-in definitions can be inspected in depth but cannot be edited or removed. Details include version, semantic role, ports, parameters, shape-rule identity, operation family, implementation support including unavailable mappings and notes, task hints, and documentation references.

Users create reusable custom authoring templates from the Nodes workspace. The wizard first chooses one of three kinds. A mathematical template accepts a bounded LaTeX-style formula or guided equation entry and is validated into NeuroWeave's safe single-input tensor expression language. A sequential block is assembled from active built-in operation nodes using manifest-driven parameter controls and validation rather than raw JSON. A public repository reference verifies a public Hugging Face model/revision and pins its resolved commit while retaining optional class metadata. Built-in definitions remain locked; custom templates can be edited or deleted and each successful edit increments the template revision.

Mathematical and sequential custom templates also appear in the Model Builder node catalog. Activating a mathematical template inserts the canonical built-in `math.expression` node with the validated expression. Activating a sequential block expands it into ordinary built-in nodes, applies the validated parameters, and connects compatible active ports in sequence. This expansion happens before model persistence, so saved graphs never depend on a custom-template ID. A repository reference remains visible as a non-executable reference until a trusted NeuroWeave adapter exists; repository code is not imported or executed.

The Settings workspace is the application-settings destination. It uses a left navigation rail and flat content sections; General explicitly states that no editable application-level settings are defined yet. It may link to installation-wide management surfaces such as Node Library and Runtime Environment, but environment-backed launch configuration (ports, paths, logs, timeouts, and similar values) is not exposed as editable Settings content. Model-specific graph and compilation configuration remains inside the corresponding model workspace.

In Datasets, the user registers a minimal typed definition through three stages: Dataset and sources, Inspect and confirm, and Register. The filesystem explorer selects real external sources; the capability registry derives CSV/TSV/Parquet and NPY/NPZ formats from the selected path, while relevant controls are shown only for the selected source. Auto Detect is visibly unavailable. After registration, the user opens the durable workspace with Overview, Validation, I/O, Processing, and Split tabs. I/O assigns input/output/metadata/unused roles and structural fields; Processing changes source interpretation and re-inspects; Split stores population and declarative strategy/fractions without materializing partitions. Validation can be rerun against the live source. Dataset cards are persisted summaries with availability state. Source files are never uploaded, copied, or deleted.

Training is intentionally a bootstrap workflow. Once at least one saved model and one persisted dataset registration are available, the user creates a training draft by choosing the model, dataset, name, epochs, and batch size. The draft is displayed as a card similar to the model library, but it cannot start execution. No training worker, fit loop, weight update, checkpoint, or persistent training record is created yet.

The Metrics route shows the server-owned built-in metric and loss catalog as read-only definitions and supports custom metric/loss authoring through a bounded formula workflow. Users may enter LaTeX directly or use a guided equation palette that edits the same source with a live KaTeX preview. Custom metric/loss definitions remain governed by the compilation capability contract.

The model overview supports architecture inspection, duplicate, links to the dedicated Export center, `.keras` architecture import, and confirmed delete. Reopening restores the graph and revision. Compilation source snapshots are revision- and profile-specific; its CodePreview is inspection/copy only. The Export center consumes the capability matrix, groups project/source/native/interchange/checkpoint methods, explains disabled formats, and shows only options supported by the selected format. Project JSON and source download from Export immediately; binary artifacts remain in the job workflow until verified success.

For binary export and functional validation, the Environment page reads API/backend/device/policy capability from `/api/metadata`. Discovery is requested only for the persisted backend/API pair when a compute feature is entered, stores the result in a fingerprinted runtime snapshot, and validates or reuses it until packages, hardware, environment, or backend configuration changes. The page shows supported memory policies per device and keeps selection session-scoped. Each export is a job: phase, device, revision, verification, cancellation, and failure diagnostics remain visible; the artifact download is enabled only after verified success. If an active job uses the current selection, users choose Stop and switch or Keep running/use the new selection later. Keras remains the model API layer; native workers use raw framework APIs and only advertise their verified profile subset.
