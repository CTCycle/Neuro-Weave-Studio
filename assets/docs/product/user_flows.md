# User Flows

Last updated: 2026-09-02

The application opens on the model catalog (`/models`). Users browse or filter saved models, select one for a read-only overview, and choose a dedicated Compilation, Export, or Inference workspace. The Model Builder (`/builder`) is reserved for creating a model; `/builder/:modelId` edits an existing architecture. In Builder, users set the execution backend and Keras/native mode, drag nodes from the catalog, connect typed ports, configure every exposed node property, validate, and explicitly save. Multiple open models use isolated tabs. Save persists the graph/profile revision; Compilation then owns capability-driven configuration, validation, and source generation. Unsaved Builder changes warn before internal navigation or browser unload.

The primary navigation also exposes Datasets (`/datasets`) and Training (`/training`). In Datasets, the user starts a wizard, selects a source type, navigates the local filesystem through the server-backed explorer, and selects the real file or folder path used by future operations. Tabular files, serialized arrays, image folders, folder-plus-reference-data layouts, document folders, audio folders, time-series files, and custom sources expose relevant interpretation options. Dataset definitions are held in session memory only. The source is not uploaded, copied, or persisted. Dataset cards provide lightweight path/source previews plus session-only Explore, Preprocessing, Smart split, and Custom split controls.

Training is intentionally a bootstrap workflow. Once at least one saved model and one session dataset reference are available, the user creates a training draft by choosing the model, dataset, name, epochs, and batch size. The draft is displayed as a card similar to the model library, but it cannot start execution. No training worker, fit loop, weight update, checkpoint, or persistent training record is created yet.

The Metrics route continues to show the server-owned built-in metric and loss catalog as read-only definitions. An Add loss / metric wizard can create a session-only custom definition. Users may enter LaTeX directly or use a guided equation palette that edits the same LaTeX source, with a live KaTeX preview. These drafts are deliberately not part of the server capability catalog and cannot yet be selected in Compilation or Training.

The model overview supports architecture inspection, duplicate, links to the dedicated Export center, `.keras` architecture import, and confirmed delete. Reopening restores the graph and revision. Compilation source snapshots are revision- and profile-specific; its CodePreview is inspection/copy only. The Export center consumes the capability matrix, groups project/source/native/interchange/checkpoint methods, explains disabled formats, and shows only options supported by the selected format. Project JSON and source download from Export immediately; binary artifacts remain in the job workflow until verified success.

For binary export and inference, the Environment page reads API/backend/device/policy capability from `/api/metadata`. Discovery is requested only for the persisted backend/API pair when a compute feature is entered, stores the result in a fingerprinted runtime snapshot, and validates or reuses it until packages, hardware, environment, or backend configuration changes. The page shows supported memory policies per device and keeps selection session-scoped. Each export is a job: phase, device, revision, verification, cancellation, and failure diagnostics remain visible; the artifact download is enabled only after verified success. If an active job uses the current selection, users choose Stop and switch or Keep running/use the new selection later. Keras remains the model API layer; native workers use raw framework APIs and only advertise their verified profile subset.
