# Node Manifest Specification

Last updated: 2026-08-18

Each manifest defines stable `id`, integer `version`, display name, category, description, input and output ports, parameter definitions, a shape-rule descriptor, v2 code-target mappings, UI metadata, deprecation state, and documentation reference. IDs use lower-case dotted names. Port and parameter IDs are unique inside the manifest. A `tensor_list` input declares its element kind explicitly (tensor by default); it is not a bypass for port-kind validation. Target mappings may declare per-parameter support, allowed values, constraints, and notes; these references must name parameters in the same manifest. Every one of the 85 manifests is exposed through a complete safe parameter contract: each parameter has a description, group, nullable/list metadata where applicable, constraints, and serializable options. Frontend controls are derived from those definitions and render every parameter; the node label is the sole layer-name control and output manifests do not expose a redundant `name` parameter. Arbitrary callables, custom Python objects, and arbitrary code remain excluded.
