# Node Manifest Specification

Last updated: 2026-09-01

Each manifest defines stable `id`, integer `version`, display name, category, description, semantic role, input and output ports, parameter definitions, a shape-rule descriptor, implementation mappings, UI metadata, deprecation state, and documentation reference. IDs use lower-case dotted names. Port and parameter IDs are unique inside the manifest. A `tensor_list` input declares its element kind explicitly (tensor by default); it is not a bypass for port-kind validation. Target mappings may declare per-parameter support, allowed values, constraints, defaults, and notes; these references must name parameters in the same manifest. Parameters may also declare recursive value schemas and visibility/enabled/required conditions. Shape-derived dimensions, including recurrent feature width, are not duplicated as editable parameters. The runtime catalog currently exposes 145 manifests through one normalized safe parameter contract; every declared parameter remains discoverable in the inspector, while target-specific capability metadata controls availability for the active Keras or native profile. Frontend controls are derived from those definitions and render every parameter; the node label is the sole layer-name control and output manifests do not expose a redundant `name` parameter. Arbitrary callables, custom Python objects, learned weights, and arbitrary code remain excluded from the portable graph contract.
